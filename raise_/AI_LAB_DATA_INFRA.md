# Data Infrastructure at AI Labs

A vocabulary guide to how leading AI research labs manage training data — with Raise API mappings for each concept.

Labs don't talk about "feature engineering" or "feature stores." They talk about **quality signals**, **curation pipelines**, **data mix**, and **evals**. The underlying operations are identical to traditional ML feature management. The vocabulary is different. This document maps lab vocabulary to Raise primitives, with concrete examples from OpenAI, Anthropic, Google DeepMind, Meta, and public datasets.

---

## Pre-Training Vocabulary

### Signals

**What labs call it**: quality signals, data signals, annotations, tags, scores, classifiers

**What it means**: A signal is any derived attribute computed from a raw document — a perplexity score, a language code, an NSFW probability, a duplicate flag. Signals are the core unit of pre-training data management. A document that enters the pipeline as raw HTML exits as a structured record with dozens of signals attached.

**In the wild**:

- **RedPajama-V2** (Together AI) computes ~40 signals per document: `perplexity_score` from KenLM, `minhash_signature`, `detected_language`, `fraction_all_caps`, `has_math`, `has_code`, and more. These signals are stored as Parquet columns alongside the document text and are the mechanism by which the 30-trillion-token corpus is filtered into training subsets.

- **FineWeb** (HuggingFace) introduces a single high-value signal: `educational_quality_score`, generated by GPT-4 on a 500K-document sample, then distilled into a FastText classifier applied to 15 trillion tokens. One signal, applied consistently, produces models that outperform equivalently-sized data from raw web text.

- **Dolma** (AllenAI) formalizes signals as "tagger outputs": each tagger writes structured spans (character-level) or document-level scores, and outputs are merged across taggers. Language identification, perplexity, URL quality, toxicity, PII, and deduplication are each a separate tagger.

- **Meta / LLaMA 3**: The LLaMA 3 paper describes "a series of quality, diversity, and safety filters" — each of these is a signal. The 15T+ token training set was assembled by filtering on combinations of these signals. The filters are described qualitatively in the paper but the signal definitions are internal.

- **OpenAI** established the pattern with GPT-2's WebText dataset: web documents were filtered by upvote signal from Reddit (a social quality proxy). Every lab has built more sophisticated signal pipelines since, but the principle — compute signals, filter on signals — is unchanged.

**The gap**: RedPajama stores 40 signals as Parquet columns. There is no versioned registry of signal definitions. When a signal computation changes (e.g., a better perplexity model), there is no lineage connecting the new signal values to the old ones. Every consumer re-reads and re-filters from scratch.

**In Raise**:
```python
# Signals are features in a feature group
documents = fs.create_feature_group("curated-documents", entity_key="doc_id")
documents.create_features_from_schema({
    "doc_id": "string",
    "text": "string",
    # Signals — derived attributes
    "perplexity_score": "float32",
    "educational_quality": "float32",
    "detected_language": "string",
    "is_duplicate": "bool",
    "is_nsfw": "float32",
    "compliance_passed": "bool",
    "include_in_training": "bool",
})

# Signal computation is a Transform
scorer = QualityScorer(
    name="educational_quality",
    dimensions=[QualityDimension.EDUCATIONAL],
    model_uri="s3://models/fasttext-edu-classifier",
    input_columns=["text"],
)
```

### Curation

**What labs call it**: curation pipeline, filtering pipeline, data curation, preprocessing pipeline, cleaning pipeline

**What it means**: Curation is the end-to-end process of converting raw data (web crawl, licensed datasets, scraped content) into a filtered, signal-enriched corpus ready for tokenization. It is the composition of signal computation and filtering rules into a workflow.

**In the wild**:

- **Dolma** uses the term most explicitly: the toolkit is positioned as a "data curation" framework. Its design — composable taggers, declarative configuration — is closest to how Raise thinks about curation. Each tagger is a curation step; the pipeline is the composition.

- **DCLM** (Apple and collaborators, 2024) frames curation as a benchmark problem: given a fixed token budget, which curation decisions produce the best downstream model? It computed signals on 240 trillion tokens — the largest publicly documented curation pipeline — to answer this question systematically.

- **Meta LLaMA 3**: The data team describes "extensive data cleaning" as a prerequisite for scaling to 15T tokens. Curation at this scale requires distributed execution (Spark), custom deduplication infrastructure, and weeks of wall-clock time.

- **Anthropic**: Curation at Anthropic is less documented publicly, but Constitutional AI implies curation extends into post-training: generated responses are curated by the model itself against constitutional principles before entering training.

**In Raise**:
```python
# CurationPipeline composes quality, dedup, and compliance steps
pipeline = CurationPipeline(
    name="pretraining_curation",
    steps=[
        QualityScorer(
            dimensions=[QualityDimension.FLUENCY, QualityDimension.EDUCATIONAL],
            thresholds=[
                QualityThreshold(QualityDimension.FLUENCY, min_score=0.6),
                QualityThreshold(QualityDimension.EDUCATIONAL, min_score=0.5),
            ],
        ),
        DeduplicationTransform(
            config=DeduplicationConfig(
                algorithm=DeduplicationAlgorithm.MINHASH,
                threshold=0.8,
                key_columns=["text"],
            ),
        ),
        ComplianceFilterTransform(
            policy=CompliancePolicy(
                name="pretraining_safety",
                rules=[
                    ComplianceRule(ComplianceFlag.NSFW),
                    ComplianceRule(ComplianceFlag.HATE_SPEECH),
                ],
            ),
        ),
    ],
)
```

### Dedup

**What labs call it**: near-deduplication, exact dedup, semantic dedup, deduplication, MinHash dedup

**What it means**: Deduplication removes or marks records that are duplicates or near-duplicates of other records in the corpus. Exact dedup removes byte-identical documents; near-dedup removes documents that are similar above a configurable threshold. Semantic dedup (rare, expensive) removes documents whose embeddings are close in vector space.

Three algorithms in widespread use:
- **MinHash LSH** — Jaccard similarity of shingle sets; fast, industry standard for near-dedup
- **SimHash** — Hamming distance on locality-sensitive hashes; faster but less accurate
- **Embedding similarity** — cosine distance on dense embeddings; most accurate, most expensive

**In the wild**:

- **RedPajama-V2** stores `minhash_signature` (128-bit MinHash) per document. Near-dedup is run across the 100-billion-document corpus to identify clusters of similar documents. The `is_duplicate` and `duplicate_cluster_id` flags are then used to filter the training set.

- **Meta LLaMA 3**: The paper explicitly describes MinHash near-deduplication as a required preprocessing step for the 15T-token corpus. Without dedup, the same content (boilerplate, syndicated articles, copy-paste from popular sources) would appear thousands of times and bias the model.

- **DCLM** found that deduplication improves model quality up to a point, then shows diminishing returns — aggressive dedup can remove valuable redundant signal (multiple phrasings of the same concept) along with true duplicates.

- **Semantic dedup** is referenced by Google DeepMind (for Gemini multimodal data) and Apple (DCLM) as an area of active research. At scale, even approximate embedding computation per document requires significant GPU-hours.

**In Raise**:
```python
dedup = DeduplicationTransform(
    name="web_dedup",
    config=DeduplicationConfig(
        algorithm=DeduplicationAlgorithm.MINHASH,
        threshold=0.8,      # 80% Jaccard similarity → near-duplicate
        key_columns=["text"],
        action="mark",      # mark_as_duplicate, don't delete
    ),
    is_duplicate_column="is_duplicate",
    duplicate_of_column="duplicate_of",
    entity_key_column="doc_id",
)
```

### Data Mix / Training Mix

**What labs call it**: data mix, training mix, domain weights, mixing strategy, sampling weights, data recipe

**What it means**: A training mix is the specification of how samples from different data sources are combined to form the training dataset. Rather than concatenating all available data, a mix assigns sampling probabilities (weights) to each source. The mix encodes both which domains are included and how frequently each is seen during training.

Mixing strategies vary:
- **Weighted**: sample proportionally to assigned weights (e.g., 70% web, 15% books, 10% code, 5% academic)
- **Temperature**: raise weights to power `1/T` before normalizing — T < 1 amplifies the dominant source, T > 1 smooths differences
- **Proportional**: sample proportional to corpus size, ignoring assigned weights

**In the wild**:

- **Meta LLaMA 3** paper describes explicit domain weights for the 15T-token mix: web (the plurality), books, code, academic papers, and other sources. The specific weights are not published, but the structure — multiple sources, explicit weights, per-language breakdowns — is described.

- **Mistral** and **Falcon** publications reference domain mixing as the primary lever for controlling what knowledge the model has. A model trained on 80% code is a code model; a model trained on 20% code + 80% general web is a general model.

- **DCLM** treats the data mix as an experimental variable: different mixes produce measurably different downstream benchmark performance. The finding that FastText-filtered data outperforms heuristic-filtered data holds across mixing strategies.

- **Anthropic** uses domain-stratified mixing for Claude's pre-training but the weights are proprietary. The multilingual capability of Claude models implies at least 20–30% non-English data in the mix.

- **OpenAI GPT-4** technical report describes a mix of internet data, licensed data, and proprietary data — but ratios are not published. The pattern of high-quality licensed data (books, code, academic) at elevated weight relative to web data is widely attributed to GPT-4's strong performance.

**In Raise**:
```python
from raise_ import MixSource, DatasetMix, MixingStrategy

sources = [
    MixSource(feature_group="web-crawl/curated", weight=0.70,
              filters=["include_in_training == True", "language == 'en'"]),
    MixSource(feature_group="books/curated",     weight=0.15,
              filters=["include_in_training == True"]),
    MixSource(feature_group="code/curated",      weight=0.10,
              filters=["include_in_training == True"]),
    MixSource(feature_group="arxiv/curated",     weight=0.05,
              filters=["include_in_training == True"]),
]

mix = DatasetMix(
    name="pretraining-v3",
    sources=sources,
    strategy=MixingStrategy.TEMPERATURE,
    temperature=0.7,          # amplify high-weight sources
    total_samples=2_000_000_000,
    seed=42,
)

# Effective sampling probabilities after temperature scaling
for src, prob in zip(["Web", "Books", "Code", "Academic"], mix.effective_weights()):
    print(f"  {src}: {prob:.1%}")
```

### Token Budget

**What labs call it**: token budget, compute budget, token count, training tokens, data budget

**What it means**: The token budget is the total number of tokens that will be processed during a training run. It determines how much data is needed and at what quality threshold. A 1T-token training run needs 1T tokens of high-enough quality to fill it; a 10T-token run needs 10T. The token budget sets the lower bound on how aggressive curation can be — too aggressive, and there isn't enough data to fill the budget.

**In the wild**:

- **Chinchilla scaling laws** (DeepMind, 2022) established the relationship: optimal performance given a compute budget requires scaling data tokens proportional to model parameters. For a 70B parameter model, the Chinchilla-optimal token count is ~1.4T tokens. This made token budget a first-class planning quantity for every subsequent model.

- **Meta LLaMA 3** trained on 15T tokens — deliberately over-trained relative to Chinchilla-optimal for a 70B model. The LLaMA team found that over-training (more tokens than Chinchilla suggests) produces better inference-time performance for a given model size, because inference is far cheaper than training.

- **DCLM** used token budget explicitly as the independent variable in its benchmark: "given 4T tokens to fill, which curation pipeline produces the best model?" The answer (FastText + aggressive dedup) depends on the budget.

- Token budget interacts with deduplication: with near-dedup applied, the available token count drops. Meta's 15T-token target required sourcing substantially more raw data to achieve the post-dedup target.

**In Raise**: Token count is stored as a feature; the token budget is expressed as `total_samples` in `DatasetMix`:
```python
# Feature: token count per document
documents.create_features_from_schema({
    "token_count": "int64",
})

# Budget: total_samples × avg_tokens_per_sample ≈ token budget
mix = DatasetMix(
    name="pretraining-v3",
    sources=sources,
    total_samples=2_000_000_000,   # 2B samples × ~7.5 tokens/sample ≈ 15T tokens
)
```

### Synthetic Data

**What labs call it**: synthetic data, model-generated data, AI-generated data, distillation data, augmented data

**What it means**: Data generated by a model (often a stronger model) to supplement or replace human-authored data. Synthetic data is used across both pre-training (generating text in low-resource domains) and post-training (generating instruction-following examples, preference pairs, and RLAIF annotations).

**In the wild**:

- **Phi series** (Microsoft): Phi-1, Phi-1.5, Phi-2, and Phi-3 are trained predominantly on synthetic "textbook quality" data generated by GPT-4 and filtered to be more coherent and educational than raw web text. The key insight: a small model trained on high-quality synthetic data can match a much larger model trained on noisy web data.

- **Anthropic Constitutional AI**: Anthropic generates synthetic preference data at scale by having an early model revise its own responses against constitutional principles, then using those (prompt, revision) pairs as SFT data. A second stage generates preference labels synthetically — the model judges which of two responses better satisfies the constitution, without human annotators.

- **Meta LLaMA 3**: The technical report describes using Llama 3 itself to generate synthetic data for fine-tuning Llama 3 — a self-distillation loop. This includes synthetic coding examples, math problem solutions, and multilingual translations.

- **FineWeb**: The educational quality classifier was trained on GPT-4-generated quality scores. This is a form of synthetic annotation: GPT-4 labels are synthetic (AI-generated) relative to human ground truth, but are used to train a production classifier.

- **Google DeepMind SynthID**: DeepMind watermarks synthetic content — images and text generated by their models — so that synthetic provenance can be tracked. This is data management for synthetic data: every AI-generated document carries a signal indicating its origin model.

**In Raise**:
```python
# Synthetic data is tracked via provenance
synthetic_provenance = DatasetProvenance(
    source_name="LLaMA-3-70B-synthetic",
    source_uri="s3://acme-datasets/synthetic/llama3-70b/",
    collection_date=datetime(2024, 9, 1),
    license="Generated — see legal/synthetic-data-policy.pdf",
    metadata={
        "generator_model": "meta-llama/Llama-3-70b-instruct",
        "generation_method": "constitutional_revision",
        "num_revisions": 3,
        "is_synthetic": True,
    },
)

# Feature to track synthetic origin
documents.create_features_from_schema({
    "is_synthetic": "bool",
    "generator_model": "string",
    "generation_prompt_hash": "string",
})
```

### Data Flywheel

**What labs call it**: data flywheel, virtuous cycle, data-model feedback loop, self-improvement loop

**What it means**: A data flywheel is a positive feedback loop where model quality improvements lead to better data, which lead to better model quality. The loop: a stronger model generates higher-quality synthetic data → the synthetic data improves the next model → the improved model generates even better data. Labs with a deployed product have an additional loop: user interactions surface distribution shift and failure modes → these become new training examples → the model improves on real usage.

**In the wild**:

- **OpenAI / ChatGPT**: The most explicit flywheel in the industry. ChatGPT user interactions (with consent) surface what users actually ask and where the model fails. Especially compelling examples (whether impressive or problematic) become candidates for inclusion in future SFT or RLHF datasets. The scale of ChatGPT's deployment makes this flywheel exceptionally fast.

- **Anthropic**: Claude's conversations with users surface ambiguous cases for Constitutional AI principles. The model's constitutional self-critiques produce training examples that are directly relevant to real failure modes. The Claude model spec is iteratively refined based on cases that the current model handles poorly — closing the loop from deployment back to principle definition.

- **Google**: Search queries + Google Assistant interactions + YouTube recommendations provide a flywheel for Gemini fine-tuning. The scale of Google's product surface (billions of daily queries) makes this one of the most powerful flywheels in existence.

- **Meta**: Llama's deployment as an open-weight model creates an inverted flywheel — the community discovers failure modes and useful capabilities, and Meta observes this externally. Less controllable than a product flywheel, but provides signal at massive scale.

**In Raise**: The flywheel is expressed as a feedback loop between post-training evaluation and data collection. Eval failures → new training examples → next model version:
```python
# Eval failures become new training examples
eval_failures = fs.get_feature_group("post-training/eval-failures")

# Conversion job: eval failures → SFT examples
failure_to_sft = fs.create_job(
    name="eval_failures_to_sft",
    sources=[FeatureGroupSource(
        feature_group="post-training/eval-failures",
        filters=["severity >= 0.7", "is_recoverable == True"],
    )],
    target=Target(feature_group="post-training/sft-demonstrations"),
)
```

## Post-Training Vocabulary

### Demonstrations

**What labs call it**: demonstrations, SFT data, instruction data, supervised data, instruction-following data, RLHF supervised phase

**What it means**: Demonstrations are (input, output) pairs where the output represents the desired model behavior — the "gold" response to a prompt. They are used in Supervised Fine-Tuning (SFT) to teach the model what format, style, and content is expected. Demonstrations are the first stage of post-training.

High-quality demonstrations are expensive: they require skilled writers who can produce ideal responses across many domains and styles. The shift toward AI-generated demonstrations (via synthetic data) is partially driven by the cost of human demonstration generation.

**In the wild**:

- **OpenAI InstructGPT**: The paper describes hiring contractors via Scale AI to write demonstrations for 13K prompts — responses that represent what a helpful, harmless assistant should say. These demonstrations were the SFT training data for InstructGPT.

- **Anthropic**: Demonstrations for Claude were initially human-written, then supplemented heavily by Constitutional AI revisions — the model rewrites its own harmful responses into non-harmful demonstrations.

- **Meta LLaMA-3-Instruct**: Meta used both human-annotated and synthetically generated demonstrations for instruction tuning. The synthetic demonstrations were generated by Llama 3 itself on diverse task types.

- **Open datasets**: Alpaca (Stanford, 2023) was one of the first publicly released demonstration datasets: 52K instruction-response pairs generated by GPT-3.5 from a seed set of human-written examples. OpenHermes, ShareGPT, FLAN — all are demonstration datasets curated from various sources.

**In Raise**:
```python
# Demonstrations are stored in a feature group
sft_data = fs.create_feature_group(
    "sft-demonstrations",
    entity_key="example_id",
)
sft_data.create_features_from_schema({
    "example_id": "string",
    "prompt": "string",
    "response": "string",
    "domain": "string",           # coding, math, creative, safety, etc.
    "quality_score": "float32",
    "annotator_type": "string",   # "human", "model", "synthetic"
    "model_version": "string",    # if annotator_type == "model"
    "include_in_training": "bool",
})
```

### Preference Data

**What labs call it**: preference data, comparison data, RLHF data, ranking data, human feedback, chosen/rejected pairs

**What it means**: Preference data consists of (prompt, chosen response, rejected response) triplets where a human (or AI judge) has indicated that `chosen` is preferable to `rejected`. This is the training signal for reward models and for Direct Preference Optimization (DPO). Unlike demonstrations, preference data doesn't require knowing the correct answer — only a relative ranking.

**In the wild**:

- **OpenAI InstructGPT**: After the SFT phase, labelers were shown pairs of model responses and asked to rank them. These rankings (330K comparison pairs) trained the reward model used in PPO.

- **Anthropic**: Preference data at Anthropic is generated partly by human annotators (for ambiguous cases and calibration) and partly by AI feedback under Constitutional AI. The AI judge compares two responses against a principle and generates a preference label.

- **HH-RLHF dataset** (Anthropic, public): A released dataset of ~160K helpfulness and harmlessness preference pairs. Each entry is a conversation with a human and two model responses, labeled by which response is more helpful or less harmful.

- **Nectar** (Berkeley), **UltraFeedback** (open): Community efforts to collect large-scale preference data using strong frontier models as judges — the "LLM-as-judge" pattern for preference labeling.

**The preference format**:
```json
{
  "prompt": "Explain quantum entanglement to a 10-year-old.",
  "chosen": "Imagine two magic coins...",
  "rejected": "Quantum entanglement is a phenomenon where two particles...",
  "preference_source": "human",
  "annotator_agreement": 0.82,
  "chosen_ref_logprob": -12.4,
  "rejected_ref_logprob": -18.9
}
```

**In Raise**:
```python
preference_data = fs.create_feature_group(
    "preference-pairs",
    entity_key="pair_id",
)
preference_data.create_features_from_schema({
    "pair_id": "string",
    "prompt_id": "string",
    "chosen": "string",
    "rejected": "string",
    "preference_source": "string",  # "human", "model", "constitutional_ai"
    "annotator_agreement": "float32",
    "chosen_ref_logprob": "float64",
    "rejected_ref_logprob": "float64",
    "preference_margin": "float64",
    "include_in_training": "bool",
})
```

### RLHF / RLAIF / DPO

**What labs call it**: RLHF (Reinforcement Learning from Human Feedback), RLAIF (RL from AI Feedback), DPO (Direct Preference Optimization), PPO, reward modeling

**What it means**: These are the training algorithms that use preference data to align the model. They are not data formats — they are methods. But understanding them is necessary because they determine what data schema is required.

- **RLHF with PPO**: Train a reward model on preference pairs → use it to score model outputs during RL training. Requires: preference pairs + reward model checkpoints
- **RLAIF**: Use a frontier AI model as the preference judge instead of humans. Requires: same data schema as RLHF, but the preference labels are AI-generated
- **DPO**: Directly optimize on (prompt, chosen, rejected) without a separate reward model. Requires: reference model log-probabilities stored alongside the data

**In the wild**:

- **OpenAI**: InstructGPT and ChatGPT use RLHF with PPO. The training pipeline requires storing reward scores from the reward model alongside preference data.

- **Anthropic**: Claude is trained with both RLHF and RLAIF. Constitutional AI is a specific instance of RLAIF where the AI judge applies written constitutional principles.

- **Meta LLaMA 3**: Uses DPO for instruction tuning. The critical data requirement for DPO is the reference model log-probability for both chosen and rejected responses — these must be computed offline and stored with the preference pairs.

- **Google Gemini**: Uses RLHF (details not public). The Gemini Technical Report describes human evaluation and preference collection infrastructure.

**In Raise** — the key data management implication is storing reference log-probs for DPO:
```python
# DPO requires reference log-probs stored with preference pairs
preference_data.create_features_from_schema({
    "chosen_ref_logprob": "float64",    # from reference model (offline)
    "rejected_ref_logprob": "float64",  # from reference model (offline)
    "preference_margin": "float64",     # chosen - rejected
})

# Job: compute ref log-probs and write to feature group
ref_logprob_job = fs.create_job(
    name="compute_ref_logprobs",
    sources=[FeatureGroupSource(feature_group="preference-pairs")],
    transform=PythonTransform.from_function(compute_reference_logprobs),
    target=Target(
        feature_group="preference-pairs",
        write_mode="update",   # enrich existing rows
    ),
)
```

### Red Teaming

**What labs call it**: red teaming, adversarial testing, safety testing, jailbreak testing, adversarial prompting

**What it means**: Red teaming is the practice of systematically attempting to elicit harmful, incorrect, or policy-violating outputs from the model. Red team outputs — both the prompts that succeeded in eliciting harmful outputs and the model's responses — are used as training data for safety fine-tuning. The red team finds failure modes; the training team curates those failures into alignment data.

**In the wild**:

- **Anthropic** has published the most about red teaming methodology. Their red team process involves both human red teamers and automated red teaming using smaller models to generate adversarial prompts at scale.

- **OpenAI** employed an external red team for GPT-4 before release. GPT-4's system card describes hundreds of red team hours focused on cybersecurity, bioweapons, and disinformation risks.

- **Meta**: The Llama 2 paper describes a "red team" of ~350 people who contributed >1.4M adversarial prompts. These became safety fine-tuning data for Llama-2-Chat.

- **Google DeepMind**: Gemini's technical report describes automated red teaming using adversarial prompting models. At Gemini scale, human red teaming alone is insufficient; automated red teaming can generate adversarial prompts at millions-per-day throughput.

**In Raise**:
```python
red_team_data = fs.create_feature_group(
    "red-team-results",
    entity_key="attempt_id",
)
red_team_data.create_features_from_schema({
    "attempt_id": "string",
    "prompt": "string",
    "model_response": "string",
    "risk_category": "string",     # "jailbreak", "harmful_content", "pii_leak"
    "severity": "float32",         # 0.0 – 1.0
    "succeeded": "bool",           # did the attack succeed?
    "model_version": "string",
    "red_teamer_type": "string",   # "human", "automated", "model"
    "include_in_training": "bool",
})
```

### Evals

**What labs call it**: evals, evaluations, benchmarks, held-out evaluations, capability evals, safety evals

**What it means**: Evals are structured test sets used to measure model capabilities. In AI labs, "evals" is always the shorthand — "evaluations" sounds like HR. Evals span automated benchmarks (MMLU, HumanEval, GSM8K) that take minutes to run, to human preference evaluations that take days. The eval stack is the primary signal for whether post-training is working.

Evals are not just metrics — they are datasets. Each eval consists of (prompt, expected_output) pairs or (prompt, response_A, response_B) comparison pairs. Managing evals as versioned datasets is the same problem as managing training data.

**In the wild**:

- **OpenAI**: The OpenAI Evals framework is a public eval management system — prompts, expected responses, and evaluation logic organized in a registry. The evals used to validate ChatGPT and GPT-4 are managed in this framework.

- **Anthropic**: Eval datasets at Anthropic include capability benchmarks (coding, math, science), safety evaluations (does the model refuse dangerous requests), and human preference comparisons (Chatbot Arena-style). Each Claude release is gated on passing a suite of internal evals.

- **EleutherAI LM Evaluation Harness**: The open-source standard for running language model benchmarks. Most labs run a subset of Harness benchmarks (MMLU, HellaSwag, Winogrande, TruthfulQA) continuously across training checkpoints.

- **Chatbot Arena** (LMSYS): Human preference evaluation at scale. Users compare two model responses and vote. The resulting Elo scores are the most trusted public ranking of frontier models because they reflect real user preferences rather than artificial benchmark performance.

**In Raise**:
```python
eval_results = fs.create_feature_group(
    "eval-results",
    entity_key="result_id",
)
eval_results.create_features_from_schema({
    "result_id": "string",
    "eval_name": "string",          # "mmlu", "humaneval", "alpacaeval"
    "model_checkpoint": "string",
    "dataset_version": "string",    # which training dataset this model was trained on
    "score": "float64",
    "num_examples": "int64",
    "eval_date": "timestamp",
    "eval_type": "string",          # "automated", "llm_judge", "human"
})

# Query: find training dataset version that produced best HumanEval score
best_run = eval_results.get_entity(
    filters=["eval_name == 'humaneval'"],
    order_by="score DESC",
    limit=1,
)
```

### Alignment

**What labs call it**: alignment, safety, harmlessness, helpfulness, HHHA (helpful, harmless, honest)

**What it means**: Alignment is the goal — making the model behave according to human values and intentions — not a data format. It is achieved through the combination of demonstrations (SFT), preference data (RLHF/DPO), red teaming, and evals. Understanding alignment is necessary because it motivates the data infrastructure: every component of post-training data management is in service of alignment.

**In the wild**:

- **Anthropic** has made alignment their central research focus. Constitutional AI is Anthropic's approach to scalable alignment: rather than relying on human judgment for every preference label, alignment principles are written down as a constitution and applied at scale by the model itself.

- **OpenAI's Superalignment** initiative focuses on scalable oversight — how to align models that are smarter than humans. The data infrastructure question is: how do you evaluate and curate training data for capabilities that humans can't directly assess?

- **Anthropic's model spec** (public) is the most transparent published alignment document. It describes the hierarchy of values Claude should exhibit. The model spec is a data-generating document: it produces training signals when the model is evaluated against it.

**In Raise**: Alignment is expressed through compliance policies and evaluation criteria, not as a single feature:
```python
alignment_policy = CompliancePolicy(
    name="claude_model_spec_v1",
    rules=[
        ComplianceRule(ComplianceFlag.HARMFUL_CONTENT, action=ComplianceAction.FILTER),
        ComplianceRule(ComplianceFlag.PII, action=ComplianceAction.REDACT),
        ComplianceRule(ComplianceFlag.DECEPTIVE, action=ComplianceAction.FILTER),
    ],
)
```

## Cross-Cutting Concepts

### Training Run & Checkpoint

**What labs call it**: training run, run, experiment, checkpoint, model checkpoint, snapshot

**What it means**: A training run is a single execution of the training loop from a starting point (random or pretrained weights) to a final model. Checkpoints are model weight snapshots saved at intervals during a run. Checkpoints are used for evaluation, recovery from failures, and as starting points for subsequent fine-tuning runs.

**Critical distinction**: In Raise, "checkpoint" means an incremental processing checkpoint — the last-processed timestamp or record ID used to restart a failed job. In lab vocabulary, "checkpoint" means a model weight snapshot. These are different concepts with the same word.

**In Raise**: Training runs and model checkpoints are metadata tracked in feature groups — Raise stores the data, not the weights:
```python
training_runs = fs.create_feature_group("training-runs", entity_key="run_id")
training_runs.create_features_from_schema({
    "run_id": "string",
    "dataset_version": "string",    # which DatasetVersion this run used
    "model_architecture": "string",
    "started_at": "timestamp",
    "completed_at": "timestamp",
    "num_tokens_trained": "int64",
    "best_checkpoint_step": "int64",
    "final_eval_score": "float64",
})
```

### Data Card / Dataset Card

**What labs call it**: data card, dataset card, model card (for the model side), datasheet

**What it means**: A data card is a structured document that describes a dataset: its sources, collection methodology, intended uses, known limitations, and licensing. HuggingFace dataset cards, Google's Data Cards, and academic datasheets serve this function. They are the human-readable provenance record alongside the machine-readable provenance tracked by systems like Raise.

**In the wild**:

- **HuggingFace Hub**: Every dataset on the Hub has a dataset card in `README.md`. RedPajama-V2, Dolma, FineWeb all have detailed cards describing their pipeline, signals, and licensing.
- **Google's Data Cards Playbook**: A methodology for creating structured dataset documentation, used internally for Google datasets.

**In Raise**: `DatasetProvenance` captures the machine-readable equivalent:
```python
provenance = DatasetProvenance(
    source_name="CommonCrawl-2024-Q1",
    source_uri="s3://commoncrawl/crawl-data/CC-MAIN-2024-10/",
    collection_date=datetime(2024, 3, 1),
    license="CC0",
    language_codes=["en", "zh", "es", "fr", "de"],
    pii_reviewed=True,
    consent_documented=False,   # public web crawl
    metadata={"crawl_pages": 3_800_000_000, "pipeline_version": "v2.4"},
)
```

### Ablation

**What labs call it**: ablation, ablation study, component ablation, data ablation

**What it means**: An ablation study removes or modifies one component of the system to measure its contribution. In data infrastructure, ablation is used to determine which signals, filters, or mixing weights matter most. "We ablated deduplication" means we trained a model without deduplication and compared performance against the full pipeline.

**In the wild**:

- **DCLM** is structured as a large-scale data ablation: systematically varying the filtering strategy (heuristics vs. FastText vs. LLM-based) while holding compute constant. Each variant is an ablation of the curation pipeline.

- **Meta LLaMA 3**: The paper describes ablations over data mix ratios to justify their domain weights. Each ablation requires a separate training run — the data infrastructure must support rapidly producing new dataset versions with modified mixes.

**In Raise**: Ablations are expressed as `DatasetVersion` variants derived from a common parent:
```python
# Baseline version
v1 = DatasetVersion(
    name="pretraining",
    version="v1.0-baseline",
    feature_group="foundation/training-mix",
    applied_filters=["quality_score >= 0.5"],
    num_records=1_000_000_000,
)

# Ablation: remove deduplication
v1_no_dedup = v1.derive(
    version="v1.0-ablation-no-dedup",
    applied_filters=["quality_score >= 0.5"],  # no is_duplicate filter
    num_records=1_200_000_000,                 # more records without dedup
    metadata={"ablation": "no_deduplication"},
)

# Ablation: higher quality threshold
v1_high_quality = v1.derive(
    version="v1.0-ablation-high-quality",
    applied_filters=["quality_score >= 0.7", "is_duplicate == False"],
    num_records=600_000_000,
    metadata={"ablation": "quality_threshold_0.7"},
)
```

## The Unified Gap

Synthesizing across labs and vocabulary clusters, the gap has a consistent shape:

**What exists (good):**
- Distributed compute — Ray (OpenAI), JAX/Spark (DeepMind), PyTorch distributed (Meta)
- Object storage — S3, GCS, HDFS at exabyte scale
- Annotation vendors — Scale AI, Labelbox for human annotation at volume
- Individual pipeline tools — Dolma tagger framework, FineWeb classifier, DCLM benchmark
- AI feedback at scale — Constitutional AI (Anthropic), RLAIF (various)

**What doesn't exist (the gap):**
- A **signal registry** with versioned definitions, lineage, and schema — RedPajama computes 40 signals and stores them as Parquet columns with no registry
- A **managed curation pipeline** that tracks which version of which classifier ran on which corpus snapshot — DCLM shows this matters enormously; nobody has a system for it
- A **dataset version store** that links `DatasetVersion("llama-3-pretrain", "v1.0")` to exact filters, signal thresholds, and mixing weights — labs use README files and institutional memory
- A **post-training data store** that tracks preference pairs, reward scores, and annotation quality across RLHF iterations with lineage — currently JSON files in S3 with naming conventions
- A **unified eval registry** that tracks model checkpoint × eval suite × score with queryable history — currently spreadsheets and custom dashboards

The result: when a model regresses between checkpoints, teams manually compare spreadsheets, Git history, and Parquet metadata to trace what changed. When annotation quality drops, there is no automated alert. When a new dataset version is created, lineage back to the raw crawl lives in a README.

OpenAI's internal data agent (a Codex-powered LLM that reads internal data tables and writes enriched metadata) is evidence that the gap is felt at the frontier: they built an LLM to understand their own data rather than building a proper registry. That is the problem Raise is designed to solve.
