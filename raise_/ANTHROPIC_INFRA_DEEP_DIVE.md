# Anthropic Infrastructure Deep Dive

A workflow-by-workflow account of Anthropic's data and training infrastructure — from raw crawl to deployed Claude model. Follows the same structure as the OpenAI deep dive for side-by-side comparison. Sourced from primary documents (papers, blog posts, job postings, model cards, RSP documents) with inferences clearly flagged.

The core differences from OpenAI at a glance: Anthropic runs a **three-platform compute strategy** (AWS Trainium2 + Google TPUs + NVIDIA GPUs) rather than a single cloud, uses **JAX** rather than PyTorch as the primary training framework, generates a significant fraction of post-training data via **Constitutional AI** (AI self-critique) rather than pure human annotation, and treats **mechanistic interpretability** as a first-class infrastructure concern rather than a research sideline.

## Phase 1: Pre-Training Data Preparation

### Acquisition

Anthropic's pre-training data comes from several confirmed sources (Claude 4 System Card):

- **Web crawl**: Anthropic operates its own general-purpose web crawler via the **ClaudeBot** user-agent string. It follows robots.txt conventions and does not access password-protected or CAPTCHA-gated content. ClaudeBot crawls public web pages on a continuous or periodic schedule and stores raw content in object storage.
- **Public internet data**: "Publicly available information on the Internet as of [cutoff date]" — knowledge cutoff for Claude 3 family was August 2023; Claude 3.7 Sonnet was October 2024 (trained through November 2024).
- **Third-party licensed data**: Non-public datasets licensed from third-party providers (content type and vendors not disclosed).
- **Human-generated data**: Data from annotation services, paid contractors, and the Scale AI / Surge AI annotation workflow.
- **User opt-in data**: Claude users who have opted into having their conversations used for training.
- **Internally generated data**: Synthetic data generated by Anthropic's own models, including Constitutional AI revisions and RLAIF preference labels.

### Filtering

Anthropic published a dedicated paper on pretraining data filtering for safety (2025): "Enhancing Model Safety through Pretraining Data Filtering" (alignment.anthropic.com).

**Methods tested for CBRN (chemical, biological, radiological, nuclear) content:**
1. Finetuned constitutional classifiers — supervised classifier trained on labeled harmful/harmless documents
2. Prompted constitutional classifiers — a language model prompted to judge content against CBRN-specific constitutional principles
3. Six classification methods in total across varying specificity

**Results**: Medium-strength filtering reduced harmful-capabilities eval scores by **33% relative** (from 33.7% to 30.8% harmful response rate on targeted evaluations) with no significant degradation on MMLU, Code, or Prose benchmarks. This demonstrates that safety filtering of pretraining data can be surgical — targeted at specific harm domains without broad capability regression.

**Multi-stage funnel** (inferred from job posting language + the filtering paper): Same architecture as the industry standard — heuristics (regex, length filters) → FastText classifiers → neural classifiers → constitutional LLM judges on a sample. The constitutional classifier layer is Anthropic-specific: rather than a generic NSFW/toxicity classifier, they apply principle-structured classifiers that reason about specific harm categories.

### Dual-Cloud Storage Architecture

Unlike OpenAI (Azure-only), Anthropic operates on two clouds simultaneously, which means its storage architecture is necessarily multi-cloud:

```
AWS S3 — training-adjacent storage
  ├── Raw crawl data (WARC / JSONL)
  ├── Processed training Parquet shards
  ├── Interpretability activation caches (100TB+ for SAE training)
  └── Model checkpoints (Orbax format)

Google Cloud Storage (GCS) — analytics-adjacent storage
  ├── Event data, product telemetry
  ├── Data ingested via Fivetran / Segment
  └── Source data for BigQuery pipelines

BigQuery — analytical warehouse
  ├── Product metrics, usage data, annotation metadata
  ├── Eval results, safety evaluation scores
  └── Training run metadata and lineage
```

The split reflects the organizational reality: training runs primarily on AWS (Trainium2) and Google (TPU), so training data lives close to each cluster. Analytics and business data runs on GCP (BigQuery is Google's primary analytical product) because of the Google Cloud partnership. This means Anthropic's data engineers must manage cross-cloud data movement — Fivetran and Segment handle ingestion from various sources into GCS/BigQuery; training data pipelines in Spark read from S3.

## Phase 1b: Data Engineering Infrastructure

### The Research Data Platform

Anthropic has a dedicated **Research Data Platform** engineering team whose charter is explicitly data infrastructure for ML research — not general-purpose business data. From the job posting:

> "ETL pipelines extracting data from training runs into queryable storage. Dataset management with provenance tracking and lineage. ML experiment tracking (monitoring RL runs, exploring finetuning datasets). Tools using: Spark, BigQuery, DuckDB, Parquet."

This is the closest thing to a managed feature store that Anthropic has built internally. It is custom-built because no commercial product handles the combination of training-run provenance, signal-enriched document storage, and experiment tracking in a single system.

### Processing Stack

| Layer | Confirmed Technology |
|---|---|
| Distributed processing | Apache Spark |
| Interactive analytics | DuckDB over Parquet |
| Transformations | dbt |
| Orchestration | Apache Airflow / Cloud Composer |
| Ingestion | Fivetran, Segment |
| Infrastructure | Terraform + Kubernetes |
| Columnar format | Apache Parquet |

**Spark** handles large-scale batch processing — signal computation, language identification, deduplication across the full pre-training corpus. Spark jobs run on ephemeral clusters (Dataproc on GCP, EMR on AWS) rather than persistent clusters, which aligns with the batch-processing access pattern of pre-training data pipelines.

**dbt** manages SQL-based data transformations in BigQuery — the dependency graph of transformations from raw event data to derived analytical tables. dbt's lineage tracking (each model knows its upstream dependencies) is the closest thing to feature lineage that lives in BigQuery.

**Airflow / Cloud Composer** orchestrates the DAG of pipeline stages. Cloud Composer is GCP's managed Airflow service, which integrates natively with BigQuery, GCS, and Dataproc — consistent with Anthropic's primary analytics cloud being GCP.

### Concurrent Signal Enrichment

The same concurrency challenge as at any large lab: multiple teams computing different signals (quality scores, language IDs, constitutional classifier outputs, dedup flags) against the same base corpus. The pattern most consistent with Anthropic's confirmed Spark + Parquet stack is **separate signal stores joined at read time**:

- Quality team writes `quality_scores/year=2024/month=03/*.parquet`
- Dedup team writes `dedup_flags/year=2024/month=03/*.parquet`
- Constitutional compliance team writes `cbrn_scores/year=2024/month=03/*.parquet`
- Final training pipeline joins on `doc_id` to produce the enriched training set

This avoids write conflicts entirely. The join cost at training set preparation time is acceptable because it's run once per training dataset version, not continuously. Iceberg or Delta Lake schema evolution is an alternative; Anthropic's stack doesn't explicitly confirm which approach, but the Spark + Parquet combination is most naturally paired with Hive-style partition writes rather than Iceberg.

### Pipeline Monitoring

From job posting language: "disaster recovery and replication requirements" for petabyte-scale data; "high-volume time-series system" for ML metrics; "petabyte-scale with thousands of users" requiring IAM/ACL management.

The Anthropic data team runs:
- **Great Expectations** style data quality checks (not confirmed specifically, but industry-standard for dbt + Spark stacks)
- **Custom time-series infrastructure** for ML training metrics (not standard Prometheus/Grafana — the Research Data Platform team builds a custom system for training run monitoring)
- **Airflow SLA monitoring** for pipeline stage completion deadlines

### Dataset Exploration

The Research Data Platform team explicitly builds "tools for exploring finetuning datasets" and "ML experiment tracking." The confirmed technology stack (DuckDB + Parquet + BigQuery) supports:

- **DuckDB**: sub-second queries over Parquet files, used for dataset exploration and quality analysis without standing up a Spark cluster
- **BigQuery**: SQL queries over training metadata, annotation results, eval scores — the analytical layer on top of operational data
- **Jupyter notebooks**: primary research interface for sampling documents, plotting signal distributions, comparing dataset versions
- **Custom Streamlit / internal UIs**: the Research Data Platform likely builds internal tools for visualizing training runs and dataset statistics, though none are publicly documented

## Phase 2: Small-Scale Experiments

### JAX and the Compilation Model

Small-scale experiments at Anthropic use the same JAX + TPU/GPU stack as the full hero runs, just on smaller slices of compute. This is a JAX design feature: the same code that runs a 1B parameter model on 8 TPUs runs a 100B parameter model on 1,024 TPUs — scaling is controlled by sharding annotations, not code changes.

```python
# JAX sharding via Mesh + PartitionSpec
mesh = Mesh(np.array(jax.devices()).reshape(8, 16), ('dp', 'mp'))

with mesh:
    # Tensor parallel: weight matrix sharded across 'mp' axis
    kernel = jax.device_put(
        kernel,
        NamedSharding(mesh, PartitionSpec('mp', None))
    )
```

The XLA compilation model means the first run of a new configuration is slow (compilation takes minutes for large models) but subsequent runs are fast. Research iteration speed favors small models where compilation is fast and results are interpretable.

### Scaling Laws

Anthropic uses scaling law extrapolation in the same spirit as OpenAI — the RSP (Responsible Scaling Policy) explicitly acknowledges "the rate of compute scaling for frontier models is approximately 4.2x per year from 2018–2024, with algorithmic efficiency adding approximately 2.8x per year." This implies Anthropic tracks scaling trajectories carefully as part of their safety planning, which requires systematic small-scale experiments to fit scaling curves.

Small-scale experiments at Anthropic also have a **safety dimension** that OpenAI's don't: the RSP requires capability evaluations when a model reaches 4x the compute of the most recently tested model. This means capability assessments must be run at intermediate scales to track whether an ASL threshold is being approached, independent of whether a production model is being built.

### Ray Tune (Inferred)

Job postings reference "the Trio async framework for concurrent experiment management" in the RL context. Ray Tune is widely used for hyperparameter search in JAX-based pipelines; Anthropic's explicit mention of Trio (an async Python library) suggests they may use a custom async experiment runner rather than Ray Tune specifically for some workloads. W&B is the most likely experiment tracker (not explicitly confirmed for Anthropic).

## Phase 3: Hero Runs

### Two Training Platforms, One Framework

Anthropic's unique infrastructure challenge is training on two fundamentally different accelerator architectures using a single codebase:

```
Platform A: AWS Trainium2 (Project Rainier)
  Chip: Trainium2 (Trn2)
  Cluster: ~500,000 chips across multiple Indiana datacenters
  Interconnect (scale-up): NeuronLink 3D torus (4×4×4, 64 chips/UltraServer)
  Interconnect (scale-out): EFAv3 (800 Gbit/s per chip)
  Framework: JAX with Neuron SDK (NKI for custom kernels)
  Compilation: XLA → Neuron compiler → Trainium2 ISA

Platform B: Google TPUs (Project Google)
  Chip: Ironwood (TPU v7) — 10x peak perf over TPU v5p
  Cluster: up to 1,000,000 chips across Google datacenters
  Interconnect: ICI (Inter-Chip Interconnect), 3D torus mesh
  Framework: JAX (native — this is what TPUs were designed for)
  Compilation: JAX → XLA → TPU HLO
```

**Why JAX works across both**: JAX compiles to XLA IR regardless of backend. The XLA compiler targets either Google's TPU lowering or AWS's Neuron compiler (which adds a Trainium2 backend to XLA). The same JAX model code runs on both platforms with different sharding configurations — the model doesn't need to know which hardware it's running on.

### Trainium2 Architecture in Detail

**The UltraServer** — the fundamental building block of Project Rainier:
```
UltraServer (4 physical servers, 2 racks):
  ├── 4 physical servers × 16 Trainium2 chips = 64 chips total
  ├── Compute: up to 83.2 FP8 petaflops
  ├── Memory: 64 × 96GB HBM3e = 6.1 TB aggregate HBM
  ├── Memory bandwidth: 64 × 2.9 TB/s = 185.6 TB/s aggregate
  └── Power: ~48 kW

NeuronLink 3D Torus (within UltraServer):
  ├── Topology: 4×4×4 — 16 chips per physical server, extended to 4×4×4 across all four servers
  ├── X/Y axes: 128 GB/s point-to-point (within-server links)
  ├── Z-axis: 64 GB/s (inter-server links, active electrical copper cables)
  └── Bandwidth: ~2 TB/s per chip to its 6 neighbors; ~1µs per hop

EFAv3 (cross-UltraServer):
  ├── Bandwidth: 800 Gbit/s per chip (Trn2 16-chip config)
  ├── Latency: 6.5µs packet latency (down from 9µs in EFAv2)
  └── Routing: top-of-rack Marvell Teralynx + Broadcom Tomahawk4
```

**Dedicated collective cores**: Trainium2 isolates collective communication resources (AllReduce, AllGather) from compute cores, enabling near-perfect compute-communication overlap. On NVIDIA GPUs, NCCL collectives compete with compute for SM resources; on Trainium2, the dedicated NeuronCore-v3 cores handle collectives independently.

**Custom kernels on Trainium2**: Rather than Triton (OpenAI's kernel language), Anthropic uses **NKI (Neuron Kernel Interface)** — AWS's tile-based kernel programming interface. NKI tiles correspond to the sbuf (scratchpad buffer) on Trainium2's NeuronCore, analogous to shared memory in CUDA. The programming model is similar to Triton: tile-based, higher abstraction than raw ISA.

### TPU Training: XLA and SPMD

On Google TPUs, JAX's SPMD (Single Program, Multiple Data) model maps directly to TPU pod execution:

**Compilation**: JAX traces the model computation graph, compiles to XLA IR, which the XLA compiler optimizes (operator fusion, layout selection, memory allocation) and lowers to TPU HLO (High Level Operations) for execution. For a large model training step, XLA fuses hundreds of operations into a small number of HLO programs — eliminating kernel launch overhead and maximizing hardware utilization.

**SPMD sharding**: All chips run the identical HLO program simultaneously. Data and model shards are specified via `PartitionSpec` annotations on weight matrices. The XLA compiler inserts collective communication operations automatically based on the sharding spec — no manual NCCL calls.

**Ironwood (TPU v7)**: 10x peak performance over TPU v5p. Claude Opus 4 was trained on Ironwood — the first public confirmation of Anthropic using the newest TPU generation. ICI (Inter-Chip Interconnect) provides the TPU pod's high-bandwidth mesh.

### Parallelism Strategy

Anthropic doesn't disclose specific parallelism configurations. The standard for JAX-based frontier model training follows the GSPMD (Generalized SPMD) approach from Google's Pathways work:

- **Data parallelism**: Different micro-batches processed simultaneously across data-parallel replicas
- **Model/tensor parallelism**: Weight matrices sharded across chips via `PartitionSpec('mp', None)` — each chip holds a slice
- **Pipeline parallelism**: Less natural in JAX's SPMD model than in PyTorch; Anthropic likely uses pipeline stages but implementation details are unpublished
- **Fully Sharded**: For very large models, optimizer states and gradients are sharded across all chips (analogous to ZeRO-3), reducing per-device memory to 1/N of the full model

### Checkpointing

JAX's native checkpoint library is **Orbax** — the standard checkpointing library for JAX models, integrated with Flax (the common JAX neural network library). Orbax saves:
- Model parameters (sharded PyTree)
- Optimizer states (sharded — large, typically 2–3x model size)
- Training step counter and RNG state
- Data loader position

Checkpoints write to S3 (Trainium2 runs) or GCS (TPU runs) via the appropriate cloud storage backend. At Anthropic's scale, a single checkpoint of a frontier model writes hundreds of GB to TB of data; the write must complete within the checkpoint interval without blocking training.

### Monitoring During Hero Runs

The Research Data Platform team's charter includes "monitoring RL runs" and tracking "training run data into queryable storage." This implies:

- **Custom time-series infrastructure**: training loss, gradient norm, learning rate, perplexity — sampled at every step, stored in a high-throughput time-series system
- **BigQuery for structured metadata**: which checkpoint corresponds to which training step, which dataset version, which eval results
- **Alerts for training instabilities**: loss spikes, gradient norm explosions, dead attention heads, NaN/Inf detection

Loss spike handling is particularly important on TPUs: XLA's static graph compilation means that when a numerical instability occurs (e.g., an attention logit overflow), the failure mode can be subtle — the program continues running but produces incorrect gradients. Detection requires monitoring output statistics, not just training loss.

### SFT Data Pipeline

SFT data at Anthropic combines:
1. Human-written demonstrations (via Surge AI and direct contractors)
2. CAI-revised responses — a model rewrites its own outputs to be more helpful/harmless (see Phase 5)

The iterated training loop (from the 2022 RLHF paper) is important: Anthropic updates SFT data and preference models on a **weekly cadence** with fresh human feedback. This means the SFT dataset is not a fixed artifact but a continuously evolving one — the Research Data Platform must version these datasets and track which version was used for each training run.

## Phase 5: Post-Training — Constitutional AI and RLHF

### The Constitutional AI Pipeline

CAI is Anthropic's distinctive contribution to post-training data infrastructure. It addresses the bottleneck of human annotation for harmful content — the most psychologically costly and difficult annotation task. By replacing human preference labels for harmlessness with AI-generated labels, CAI scales the RLHF pipeline dramatically.

**The constitution**: A document of 16+ principles (in the 2022 paper; substantially expanded in 2026) derived from:
- UN Universal Declaration of Human Rights
- DeepMind's Sparrow principles
- Apple's Terms of Service
- Non-Western philosophical frameworks
- Anthropic's internal safety research

**Phase 1 — SL-CAI (Supervised Learning from Constitutional AI)**:

```
For each red-team prompt p:
  1. Sample response y⁰ from the initial RLHF model
  2. Randomly sample a constitutional principle c
  3. Prompt critique model: "Does y⁰ violate principle c? Identify specific ways."
     → critique text q¹
  4. Prompt revision model: "Revise y⁰ to address the critique. Be helpful while adhering to c."
     → revised response y¹
  5. Repeat (critique → revise) for K iterations: y⁰ → y¹ → ... → yᴷ
  6. Collect (p, yᴷ) as supervised training data
Fine-tune the original model on {(p, yᴷ)} pairs → SL-CAI model
```

**Phase 2 — RL-CAI / RLAIF (Reinforcement Learning from AI Feedback)**:

```
For each pair of responses (yₐ, y_b) to prompt p:
  1. Randomly sample constitutional principle c from the 16-principle ensemble
  2. Prompt feedback model: "Which response better adheres to principle c: A or B?"
     → AI preference label (A or B)
  3. Collect (p, yₐ, y_b, preference) as RLAIF comparison data
  
Train Preference Model (PM) on RLAIF comparisons
Fine-tune SL-CAI policy with PPO using PM as reward signal → RL-CAI model
```

**The ensemble effect**: The random sampling of constitutional principles (rather than applying all 16 to every comparison) acts as an ensemble — different principles rate different response aspects, and averaging across principles produces more robust preference labels than any single principle. This is why RLAIF labels are comparable to human labels in aggregate even though individual labels may be noisier.

**Chain-of-thought enhancement**: The feedback model can be prompted to reason before giving its preference — "First explain which response better adheres to the principle, then give your answer." This improves label quality and provides interpretable reasoning for each preference decision.

**What CAI replaces vs. keeps human**:

| Task | Human or AI |
|---|---|
| Helpfulness preference labeling (which answer is better?) | Human (Surge AI) |
| Harmlessness preference labeling (which answer is less harmful?) | AI (RLAIF) — CAI eliminates this |
| Initial red-team prompt generation | Human (Upwork, internal) |
| Setting constitutional principles | Human (Anthropic researchers) |
| Calibration and edge case review | Human (internal quality team) |
| Safety evaluation (ASL assessments) | Human + AI (structured eval process) |

### The Updated Constitution (2026)

The January 2026 Claude's Constitution update is architecturally significant. Unlike the 2022 version (a list of principles), the 2026 version is a philosophical framework explaining *why* behaviors matter. More importantly:

> "The constitution is itself a primary training artifact — Claude uses it to generate synthetic training data: conversations applying constitutional principles, response rankings, and explanations of values."

This closes a loop: the constitution defines values → a model generates training data demonstrating those values → the next model is trained on that data. Constitutional AI becomes a **data flywheel** where better constitutions produce better synthetic training data, which produce better models, which can write better constitutions.

### RLHF Algorithm

**Primary algorithm**: PPO with KL penalty — confirmed explicitly in the 2022 paper. Key hyperparameter finding (Anthropic-specific):

> "A roughly linear relation between RL reward and the square root of the KL divergence between the policy and its initialization."

This empirical regularity governs how aggressively the KL coefficient should be set: too small and the policy reward-hacks the PM; too large and the policy barely moves from the SFT initialization. The square-root relationship lets Anthropic estimate the Pareto frontier of reward vs. KL without an exhaustive sweep.

**Iterated training**: Unlike OpenAI's InstructGPT (which describes a one-shot RLHF pipeline), Anthropic's 2022 paper explicitly describes updating preference models and RL policies on a **weekly cadence** with fresh human feedback. This means RLHF at Anthropic is an ongoing operational process — the PM and policy are retrained continuously, not once. The data pipeline must support continuous ingestion of new preference data, PM retraining, and policy updates in a rolling loop.

**Preference model scale**: Tested from 13M to 52B parameters. Larger PMs produce better-calibrated reward signals and are worth the compute cost for frontier model training. The PM training is fast relative to the main model training — a 52B PM trains in hours or days, not months.

## Phase 6: Interpretability Infrastructure

This phase has no OpenAI equivalent at the same scale or rigor. Interpretability at Anthropic is a first-class engineering concern, not a research curiosity, because it is part of the path to ASL-4 safety guarantees.

### The Interpretability Research Stack

**Published trajectory**:
- 2021: Mathematical framework for transformer circuits (attention heads, residual streams)
- 2022: Toy Models of Superposition — features stored in superposition, foundational for SAEs
- 2023: Towards Monosemanticity — 16x expansion SAE on a 1-layer MLP, ~15K features, 70% interpretable
- 2024: Scaling Monosemanticity — SAEs at 1M / 4M / 34M features on Claude 3 Sonnet
- 2025 (March): Circuit Tracing — cross-layer transcoders (CLTs), attribution graphs, applied to Claude 3.5 Haiku

### Sparse Autoencoder (SAE) Training at Scale

The Scaling Monosemanticity work required infrastructure Anthropic built specifically for interpretability:

**What SAEs do**: A sparse autoencoder is trained on the residual stream activations of a frozen language model. The encoder maps each activation vector to a sparse set of interpretable features; the decoder reconstructs the activation from those features. The hypothesis: the model stores its "concepts" as directions in activation space, and SAEs find a basis that aligns with human-interpretable concepts.

**Scale**:
- 3 SAE sizes: 1M features, 4M features, 34M features — trained on Claude 3 Sonnet (a production frontier model)
- 100TB of activation cache stored in S3 — the frozen activations of Claude 3 Sonnet on 100B+ tokens of text, precomputed and stored to avoid recomputing during SAE training
- Dead feature rates: 2% (1M), 35% (4M), 65% (34M) — the 34M SAE is near the expressivity limit of the model's activations

**The multi-pass shuffle problem** (from Anthropic's engineering blog):

SAE training requires iterating over the 100TB activation cache with shuffled order (SAEs need diverse mini-batches, not sequential text). Shuffling 100TB in-memory is impossible; naive on-disk shuffle requires 100TB of temporary storage. Anthropic's solution: a multi-pass distributed shuffle:

```
Pass 1: Each of N jobs reads 1/N of dataset (100TB/N), writes K output files
         → each job handles 10TB with 100GB/job memory
Pass 2: Reduces shuffle complexity by 100x per pass
         → 1PB becomes manageable in 3 passes
```

This eliminated data shuffling as a research bottleneck — what would have been a days-long preprocessing step became a configurable operation.

**Feature visualization pipeline** — a 3-pass distributed system to find the top-activating examples for each of 34M features:

```
Pass 1: For each feature, track K highest-activating tokens + 10K random tokens
         (sharded by dataset chunk + feature group)
Pass 2: Aggregate across full dataset — find global top-K per feature
Pass 3: Reshard by dataset for feature-grouped output files → browser-consumable
```

### Circuit Tracing (2025)

The cross-layer transcoder (CLT) is a more powerful interpretability method than SAEs — it explains not just what features exist, but how computation flows between them:

- CLT replaces each transformer MLP layer with a set of features that read from the residual stream and write to all subsequent MLP layers
- The result: a computational graph of interpretable features and their relationships
- Claude 3.5 Haiku (a production model) was analyzed with 300K–30M features; at 10M features, CLT reconstruction matches the underlying model's predictions on ~50% of prompts

**Attribution graphs**: Each inference produces a directed graph — nodes are features, edges are attribution weights (how much does feature A cause feature B?). Backwards Jacobians compute edge weights. Graph pruning removes ~90% of nodes while preserving 80% of output influence. The result: a compact, human-readable explanation of why the model produced a specific output.

**What this enables**: Anthropic can now examine whether Claude's chain-of-thought reasoning is mechanistically faithful to its computation, whether self-reported reasoning matches actual computation, and where dangerous feature patterns (deception, self-preservation) activate. This directly informs deployment safety decisions.

**Open-sourced** (March 2025): CLT training code, attribution graph computation, graph pruning, and an interactive frontend for exploring graphs. The interpretability infrastructure is becoming a shared public resource, not just an internal tool.

**Compute for interpretability**: SAE training and CLT training run on separate GPU/TPU clusters from the main training runs — they consume cached activations rather than running the live model. Compute cost: tens of thousands of GPU-hours for the large SAE experiments; substantially more for CLT at 10M+ features.

## Phase 7: Evals and Safety Gating

### The ASL Framework as Infrastructure

Anthropic's Responsible Scaling Policy (RSP) is not just a policy document — it is a **gating mechanism** that determines when a model can be deployed. The eval infrastructure must be capable of making these deployment decisions with confidence.

**Trigger conditions for capability evaluation**:
- Model reaches **4x the compute** of the most recently evaluated model
- **Mid-training** if the 4x threshold is crossed during a run
- Every **3 months** for the most capable deployed model (to account for in-context improvements and fine-tuning)

**ASL thresholds**:

```
ASL-2 (current baseline — all deployed Claude models):
  ✓ Standard safety measures
  ✓ No meaningful uplift in CBRN weapon development
  → Can deploy with standard safeguards

ASL-3 (triggered by Claude Opus 4):
  ✓ Meaningful uplift to CBRN or sophisticated cyberattack capability
  ✓ Unusual but not unprecedented risk
  → Requires: enhanced security protocols, access controls, ongoing monitoring
  → Cannot deploy if world-class red team finds meaningful catastrophic misuse risk

ASL-4 (not yet triggered):
  ✓ Autonomous AI R&D capability at frontier level
  ✓ Meaningful contribution to CBRN weapons requiring state-level resources
  → Requires: security standards comparable to top-secret government systems
  → Essentially: cannot deploy without extraordinary safeguards
```

Claude Opus 4 was the first model to trigger **ASL-3** classification, with a harmful biology response rate of 1.24% (98.76% harmless) after ASL-3 safeguards.

### Bloom — Automated Behavioral Evaluation

Anthropic open-sourced **Bloom** (github.com/safety-research/bloom) — their automated behavioral evaluation framework:

**What it does**: Takes a researcher-specified behavior description and automatically generates evaluation scenarios, runs the model, and quantifies frequency and severity of the behavior. No ground-truth labels required.

**Four released benchmarks**:
1. Delusional sycophancy
2. Instructed long-horizon sabotage
3. Self-preservation behavior
4. Self-preferential bias

**Evaluation creation time**: "a few days to conceptualize, refine and generate" — fast enough to create new evals as new capability concerns arise, not a months-long process.

**Correlation**: "Reliably distinguishes baseline from intentionally misaligned models" and "strongly correlates with human judgments" — validated against human evaluations.

This is the behavioral equivalent of what mechanical interpretability does structurally: automated detection of concerning model behaviors at scale, without requiring human evaluation of every sample.

### Continuous Eval During Training

The Research Data Platform team's charter includes "monitoring RL runs" with lineage tracking between training steps and eval results. This means:

- Benchmarks run at every N-th training checkpoint (MMLU, HumanEval, and internal safety evals)
- Results stored in BigQuery, queryable against training metadata
- Regressions in safety evals are a blocking signal — unlike capability regressions which may be acceptable, safety regressions can trigger a training pause

## Phase 8: MCP — Agent Infrastructure

### What MCP Is

Model Context Protocol (MCP), released November 2024, is Anthropic's open standard for connecting AI agents to data sources and tools. Governance was donated to the **Agentic AI Foundation (AAIF)** under the Linux Foundation in December 2025, co-founded by Anthropic, Block, and OpenAI.

**Protocol foundation**: JSON-RPC 2.0 over stateful connections. Designed after the Language Server Protocol (LSP) pattern — one protocol, many implementations.

### Architecture

```
MCP System:

  Host Application (e.g., Claude Desktop, Claude Code)
    └── MCP Client
          ├── [stdio transport] → Local MCP Server (filesystem, git, terminal)
          └── [HTTP+SSE transport] → Remote MCP Server (databases, APIs, SaaS)

MCP Server capabilities (server → client):
  Resources: Data and context (files, DB results, live streams)
  Prompts:   Templated messages and workflows
  Tools:     Executable functions (code execution, API calls)

MCP Client capabilities (client → server):
  Sampling:    Server requests LLM completion from the host
  Roots:       Server queries client's filesystem/URI boundaries
  Elicitation: Server requests additional info from users
```

**The sampling primitive** is architecturally significant: it enables recursive/agentic behavior where an MCP server can itself call the LLM. A tool server can receive a request, call the LLM for a sub-task, and incorporate that response into its output — without the host application managing the recursion. This is the foundation for multi-hop agentic workflows.

### Connection to Training Infrastructure

MCP is an **inference-time protocol** — it connects deployed Claude to external tools and data sources. It is not used in the training data pipeline directly. However:

- **Research Data Platform**: Anthropic's internal data infrastructure teams almost certainly build MCP-compatible interfaces for researchers to query training datasets, eval results, and experiment metadata through natural language
- **Claude Code**: Uses MCP natively for filesystem, git, and terminal access — Anthropic's own coding tool is built on MCP
- **Internal data agent**: Likely to emerge as a Kepler-equivalent, where an MCP server exposes Anthropic's internal datasets (70K+ datasets at similar scale to OpenAI's internal data) to a Claude-based query agent

**Why MCP matters for Raise**: An MCP server wrapping Raise's feature group and dataset APIs would give any MCP-compatible agent standardized access to training datasets, signal registries, and dataset versions. The Raise primitives map naturally to MCP primitives:

```
Raise concept          → MCP primitive
FeatureGroup           → Resource (queryable data source)
Feature query          → Tool (parameterized data retrieval)
DatasetVersion         → Resource (versioned dataset)
CurationPipeline run   → Tool (trigger pipeline execution)
Job status             → Resource (live computation state)
```

## What This Implies for Raise

Anthropic's infrastructure reveals several Raise-relevant patterns not visible in the OpenAI analysis:

1. **The CAI data flywheel is a managed data pipeline**. The constitution → critique-revision → SL-CAI data → RL-CAI preference labels loop requires versioning at every step. Which constitution version generated which critique? Which critiques survived quality filtering? Which became SFT training examples? Without a data management layer, this is a README file and a set of S3 prefixes.

2. **Interpretability creates a new class of derived features**. SAE features, CLT attribution graphs, and feature activation maps are *derived signals* computed on model activations — a new kind of "feature" that Raise's signal infrastructure should handle. The 100TB SAE activation cache in S3 with a custom multi-pass shuffle is exactly the kind of problem a managed data platform addresses.

3. **The ASL gating mechanism requires data lineage**. "This model was evaluated at ASL-3 on checkpoint X, which was produced by training run Y, which used dataset version Z" — this is a provenance chain that currently lives in documentation rather than a queryable data system. An RSP-compliant lab needs this chain to be systematic.

4. **Weekly iterated RLHF creates continuous data management requirements**. Preference data arrives continuously; the PM and policy are retrained weekly. Each iteration produces a new dataset version (fresh preference pairs + previous data). Tracking which preference data version produced which PM checkpoint, and which PM checkpoint produced which policy, requires exactly the lineage infrastructure Raise provides.

5. **Multi-cloud storage is the norm, not the exception**. Both S3 and GCS are first-class storage backends for Anthropic. Raise must be storage-agnostic — not tied to any one cloud's object storage — and its feature groups must be readable from whichever cloud the training cluster is on.
